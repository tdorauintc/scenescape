- PRs: #1979, #2028, #2050, #2036 (merged to `main`); #2056 (merged into PR 3 before it); #2037, #2109, #2129 (open). Branch stack: [Details / Context](#context-1).

### Context

- "PR N" (also "step N" or "item N" in other documents) is item N of this plan.
- PRs 1, 2, 3 and 6 are on `main`; PRs 4 → 5 → 7 are feature branches stacked on `main`; PR 8 evaluates the stack and merges it to `main`.
- Review findings are cited by the short names in [Related documents](#related-documents), e.g. "prob review G9", "yaw review E2", "z review Z1", "delta 9.1", "baseline 9.4".
- This plan and the [tuning guide](prob-tracking-imm-tuning.md) are the single source of truth: each task in [Details](#details) carries the context needed to do it. The other documents are kept for back-tracking only; finding IDs point to them, and C-n (coverage test), F-n (fix + verification test) and E-n (evaluation) to the PR 3 test plan, which keeps the test-level history (mechanisms, before / after values, sweeps).
- robot_vision fixes are test-first: the failing test lands first, then the fix with before / after values in its commit message. Verify with `make -C tracker test-robot-vision`, `RobotVisionTests --gtest_filter=...` while iterating, and `RV_SCENARIO_DIR` to record scenarios. Build from a clean build directory: one configured from `main` keeps `RV_CXX_STANDARD=17` in its cache, and the tests fail on C++20 features.
- Impact evaluation: Tracker Evaluation black-box runs from `tools/tracker/evaluation/` (`python -m run_black_box_evaluation`, `--dataset wildtrack` for Wildtrack) cover Controller Immediate, Controller time-chunking and Tracker Service; the `association` block is in `pipeline_configs/black_box_*/config/*.json`. Compare HOTA, IDF1, IDSW, DIST_T, rms_jerk and acceleration_variance with the base branch.

- Cholesky failure recovery (F-6, `c4393854f`; baseline 9.4): a failed factorisation left a half-factorised matrix with inverted diagonal entries (a variance of 4 became 0.25); a finite covariance is now symmetrized, its eigenvalues raised to a floor, with one warning. Never reached in 2 h standing, 1 h circles at 10 and 1 fps, coasts or the jump runs.
- Sigma-point weights kept at κ = 3 − n (E-1, `a222bd748`; baseline 9.4, delta 9.10): no measurable effect at 10 fps (≤ 0.001 m) or 2 fps (≤ 0.01 m); one CTRV step with a turn-rate uncertainty of 1 rad gives a mean speed of 1.84 m/s against the exact 1.82 (κ = 0: 2.51); baseline's 7.2 m/s no longer reproduces. Documented in code and README; a UT pins it.
- Contiguous measurement rows without copying (F-8, `bd70d616d`): F-2's reduced update copied rows and blocks for every model and detection; contiguous rows are now views. `track()` −4.5 % single-threaded, −4.2 % with 4 threads; outputs bit-identical.
- Double precision only (F-9, `5fb7b1878`; [review comment](https://github.com/open-edge-platform/scenescape/pull/2036#discussion_r4460501876)): F-6's eigenvalue floor is lost in float32 rounding; single-precision filters are rejected (robot_vision creates none) and a repair that cannot be factorised falls back to a diagonal factor; outputs bit-identical.

Measured on PR 4 @ `f8c55f4ec` merged with the #2036 head, against PR 4 alone (Release): robot_vision 93 of 94 pass (the new test passes; the failure was fixed in [PR 4](#pr-4-mahalanobis-association), `7b93ad99f`), all 216 scenario recordings bit-identical; PR 4 benchmark +0.2 to +0.6 % per frame (time-chunking 4.85 → 4.87 ms, Immediate with 2 cameras 8.42 → 8.47 ms), near the run-to-run noise, likely the finiteness check on every sigma-point draw.

#### Follow-up work

- Align the Tracker Service's `euclidean` association with the Scene Controller (from PR 4 open item 9, prob review 1): without `max_radius_m` the Controller gates and clusters births on the frame's average object `tracking_radius` (`5f3d75086`), the Tracker on a fixed 2 m (`kDefaultAssociationMaxRadiusM`), so the same config gives a vehicle a 10 m gate in one service and 2 m in the other. The Tracker already reads the Object Library asset list from the Manager when `scenes.source` is `api` (for shift type), so it could read `tracking_radius` too and pass it as gate and `birth_cluster_radius_m`. Decide per class (the Tracker's per-category tracking) or the Controller's per-frame average, which mixes classes; or instead deprecate `tracking_radius` in both, as ADR-0019 plans. UT for config parsing and forwarding; how-to and the object-properties how-to.
- Hysteresis on the yaw publish switch in both services (from PR 4 open item 10; yaw review 4 and 7): for tracks that have seen orientation, the Controller's `_kalman_yaw_disagrees_with_velocity` and the Tracker's `select_track_rotation` publish the velocity heading instead of the Kalman yaw at speed ≥ 1 m/s and |heading − yaw| > 0.6 rad, with single cutoffs, so the published rotation can flip by ≥ 0.6 rad near either. Decided: respect `rotation_from_velocity=false` (no heading override for such classes, always the Kalman yaw); today the override ignores it, wrong for objects that move sideways. Proposed: one robot_vision helper with hysteresis (on 1.0 m/s and 0.6 rad, off 0.5 m/s and 0.3 rad; the measured turn lag is 0.07 rad, bound 0.2) and a Python binding, called by both services with per-track state, so the thresholds are defined once instead of in `OrientationAttributes.hpp` and the Controller (`SPEED_THRESHOLD_ON`, `YAW_VELOCITY_DISAGREE_RAD`). UT: the switch near both thresholds in robot_vision, the per-track state and `rotation_from_velocity` off in both services. Production impact: the published `rotation` of tracks with orientation only.
- Per-category association window colours in the 3D view (from PR 4 open item 9, prob review 22): `assetmanager.js` draws every window with one material (0x33cc66), while the 2D view colours them per category with hard-coded CSS (person, vehicle, cyclist, apriltag; #33cc66 otherwise). Use the category asset's `mark_color` from the Object Library, which the 3D view already loads for its default geometry (one cached material per colour, 0x33cc66 without one); that also covers custom categories, which the 2D CSS does not, so consider the same for 2D. No JS unit-test framework: verify in a running stack or with a UI test.
- Birth clustering with measured and unmeasured z (from #2149 C1; with PR 5 open item 1 and PR 7 open item 3, which use the same `zMeasured` flag): a birth cluster keeps the `zMeasured` of its first detection, and `fuseGeometry` averages z over every member, including pixel boxes without measured z. With a pixel-box camera and two 3D sensors seeing two floors at the same XY, 3 of 6 camera orders merge the floors into one track at birth and 1 of 6 attaches the pixel box to the wrong floor; the track splits after 1-2 frames (production settings, legacy and #2149 local-fallback inputs alike; remote measurements, which carry measured z, are unaffected). Fix in `MultipleObjectTracker::track()` (batched birth loop): a cluster becomes `zMeasured` once a measured detection joins, and its z is fused from the measured members only (zero z information for unmeasured members in the R path, measured-only mean otherwise) + a robot_vision UT over all 6 camera orders. It changes the birth z of mixed planar + 3D clusters in legacy mode, so re-record the #2149 legacy baselines.
- Load test with the observation processor (from the #2149 evaluation): `tracker/test/load` runs only the local transform, so the per-chunk gRPC cost at scale is unmeasured (the service test covers 2 cameras × 50 objects: Transform 0.69 ms local, 3.51 ms with the 0 ms mock). Add an opt-in mode (e.g. `OBSERVATION_PROCESSOR=mock` with `MOCK_OBSERVATION_PROCESSOR_DELAY_MS`) that starts the service-test mock (`tracker/test/service/mocks/observation_processor/`) and points the Tracker at it, then compare the Transform and Queue wait stages and the end-to-end p50/p99 against the local mode at 4 cameras × 300 objects in 2D and mixed modes. Needed before the processor is used outside experiments. README section for the mode and its KPIs.
