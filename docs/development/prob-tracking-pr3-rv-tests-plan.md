## 4. Step 2: test tools (header-only, `support/`)

`support/TestUtils.hpp`, in addition to the moved helpers (`makeBox` is renamed to `makeDetection`, since it builds a `TrackedObject`; `Scenario.hpp` adds an overload from a `TruthSample`):

- `atSeconds(double)`.
- `productionConfig()`: the existing `TrackManagerConfig` with the Controller / Tracker service values (q = 1e-4, r = 0.2, P0 = 1, CV + CA + CTRV). One type drives both `FilterRun` and a `MultipleObjectTracker` (PR 4).
- `namespace idx { X, Y, Vx, Vy, Ax, Ay, Z, Length, Width, Height, Yaw, YawRate }`: state-vector indices for Q / P0 / variance assertions.
- `minEigenvalue(const cv::Mat &)`: positive-definiteness checks (here: long-run, yaw and Cholesky-recovery tests; PR 4: degenerate covariance, prob review G6).

`support/Scenario.hpp`, composed as truth → sensor → filter run:

```cpp
// Unicycle truth (straight / accelerate / turn segments), finely integrated, sampled at fps.
auto truth = Trajectory({.speed = 5, .box = kCar})
               .straight(3).turn(0.5, 3).accelerate(-10, 1).straight(2) // turn, then sudden stop
               .sample(10.0);                                           // std::vector<TruthSample>

Sensor camera;                        // position, size and yaw noise std, orienting flag, seeded RNG
Sensor lidar{.orienting = true};      // reports heading as yaw, sets has_orientation

FilterRun run(productionConfig());    // wraps MultiModelKalmanEstimator; initializes on the first observation
auto states = run.feed(observe(between(truth, 0, 10), camera)); // one state per update
run.feed(observe(between(truth, 10, 11), lidar));               // switch sensor mid-run
run.coast(1.0);                                                 // predict only
run.state();                                                    // combined state; run.estimator for per-model access
```

- `Trajectory` has only `straight`, `accelerate`, `turn`; speed is clamped at 0, so a stop is `accelerate(-a, t)` and standing is `straight` at speed 0. The object size is part of the truth: a generic `Box` in the starting `TruthSample`, with `kCar` and `kPerson` presets, e.g. `Trajectory({.speed = 1.5, .box = kPerson})`.
- `Sensor` and the C-7 case table are plain aggregates set up with designated initializers, e.g. `{.name = "turn", .truth = ..., .maxPositionError = 0.3}`, so no builder methods or constructors are needed.
- Recording (#2086): `FilterRun(config, &recorder, trackId)` writes ground truth, detections, tracks and the per-step estimator state to `$RV_SCENARIO_DIR/<Suite>.<Test>/[<case>/]` (nothing when unset). `Sensor::id` names the sensor, `Box::category` the class. Plots and videos: `tools/tracker/evaluation/visualization`.
- `between(samples, t0, t1)` slices time. Sensor switches are done by editing the `Sensor` between `feed` calls, and changes of the object itself (e.g. the F-5 height step) by editing the sampled truth, so no concatenation or callback API is needed.
- States are plain copies: since F-3, `TrackedObject` copies own their matrices, so the `snapshot()` clone helper was removed (yaw review E2).
- PR 4 uses: `FilterRun` + `Trajectory` + `coast` for Mahalanobis gate tests with all three models (prob review G2, G7), competing tracks (G10), the radius ceiling (G4) and the mixture vs best-model covariance evaluation during a turn; an orienting `Sensor` near ±π for the yaw-wrap test (yaw review 3).
- Not added: a tracker-level runner (no PR 3 or PR 4 test needs it). The reference linear Kalman filter stays local to its only test (C-2).
- Sanity tests `ScenarioSupportTest.TrajectoryKinematics` (a circle closes after 2π/ω (`std::numbers::pi`), braking clamps speed at 0) and `ScenarioSupportTest.ObserveReportsTruthWithSensorNoise` (noise-free sensors report the truth; position, size and yaw noise have the configured spread).

E-2 analysis (`d673ef83a`, Release, 5 seeds unless noted; steady turn = car at 3 m/s, 0.5 rad/s, window 3–6 s):

- Mechanism: under production r, CTRV holds about half of the probability (car circle μ CV / CA / CTRV .25 / .27 / .48), and mixing with the straight CV and CA states dilutes its turn rate (0.30 for 0.5 rad/s). A CTRV-only filter has no offset (circle −0.02 / 0.00, steady turn −0.04 / −0.07 m). Before F-1 the steady turn was at −0.37 / −0.37 m.
- The steady-turn window is dominated by the turn onset: CTRV leads from about 1.4 s into the turn; cross-track peaks at −0.44 m. The settled offset is the circle's.
- It does not depend on the sensor noise: steady turn −0.17 / −0.28 m for 0, 0.05, 0.2 and 0.45 m (20 seeds); the filter's own 2σ position band is ±0.44 m. Only r moves it: r = 0.05 gives −0.09 / −0.18, r = 0.0025 (the test camera) −0.02 / −0.04 m, but CA then wins every turn (μ .75).
- Not levers (steady turn / car circle): Markov-predicted μ −0.18 / −0.30 and −0.10 / −0.27; no [min, max] rescale −0.25 / −0.30 and +0.07 / −0.11 (CA wins at μ .86 / .90, CTRV's w stays 0); CTRV keeps its own w in mixing −0.14 / −0.24 and −0.10 / −0.19 (w 0.40 / 0.46), with acceleration too CTRV loses the circle to CA (μ .25); {CV, CTRV} −0.10 / −0.21 (person circle along −0.53); {CA, CTRV} −0.12 / −0.22.
